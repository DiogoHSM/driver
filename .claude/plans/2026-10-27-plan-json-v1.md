# Plano: formato do grafo de plano (`plan.json`) do DRIVER

## Contexto

DRIVER é um plugin de Claude Code que impõe o método Discover · Route · Implement · Validate · Evolve · Release. O ADR-002 define que o artefato central é um grafo de blocos com estado; o ADR-009 (Proposto) fixa o local `.claude/driver/plan.json`, mas o formato não existe. Tudo depende dele: mod do diagrama, hook de gates, rastreabilidade requisito→bloco→teste→release, packs.

Premissas aceitas pelo usuário nesta sessão:
- TypeScript para plugin e mod.
- `plan.json` versionado no git do projeto do usuário; histórico via commits, sem `plan-v1.json`.
- Escopo v1: fases, blocos, estados, dependências, requisitos ligados, provedor por bloco, flags de gate. Fora: custo, épicos, análise de impacto automática (reservar campos opcionais).

Fato que dirige o design: `plan.json` está no git, logo **cada worktree tem uma cópia desatualizada**. Escrita precisa ir para o checkout principal, por um escritor único.

Entregável: schema zod + JSON Schema gerado, biblioteca TS (reducer puro + adaptador de I/O), CLI `driver`, hooks de gate, dois exemplos (web e vídeo), exportador Mermaid, ADRs. Sem mod e sem skills nesta rodada.

## Design

### 1. Layout em `.claude/driver/` (criado por `driver init`)

```
plan.json                 commitado, snapshot canônico
events.jsonl              commitado, ledger append-only (.gitattributes merge=union)
log/REL-1.jsonl           commitado, journal rotacionado a cada Release
blocks/B-001.md           commitado, texto longo por bloco (Spec, Critérios de aceite, Notas, Handoff)
requirements/R-001.md     commitado, opcional
decisions/D-001.md        commitado, decisões de Evolve e re-baselines
discover/{interview,assumptions,non-goals}.md
exports/plan.mmd          gitignored, regenerado por `driver export`
.lock/ .tmp/              gitignored
```

Caminho do markdown é implícito pelo id (`blocks/<id>.md`); o JSON não guarda path.

### 2. Schema (zod é a fonte; tipos abaixo)

```ts
type PhaseId = 'discover'|'route'|'implement'|'validate'|'evolve'|'release';
type BlockStatus = 'not_started'|'in_progress'|'blocked'|'in_review'|'done'|'needs_rework';
interface Actor { kind: 'model'|'user'|'hook'; id: string }

interface PlanV1 {
  $schema?: string;
  schemaVersion: 1;
  project: { name: string; packs: string[]; createdAt: string };
  revision: number;        // +1 em toda escrita (CAS e detecção de mudança pelo mod)
  baseline: number;        // 0 até o Gate 1; +1 por re-baseline no Evolve
  updatedAt: string;
  currentPhase: PhaseId;   // desnormalizado para o hook
  nextId: { R: number; B: number; D: number; REL: number };
  gates: { route: Gate; release: Gate };          // chave = fase que o gate libera
  requirements: Record<string, Requirement>;      // 'R-001' → ...; lookup O(1) em jq, diffs estáveis
  blocks: Record<string, Block>;                  // 'B-001' → ...
  baselines: BaselineEntry[];
  releases: Release[];
  ext?: Record<string, unknown>;                  // namespace por pack: ext['driver-web']
}
interface Gate { approved: boolean; approvedAt?: string; approvedBy?: string; atBaseline?: number; revokedAt?: string; revokedReason?: string }
interface Retirement { at: string; decision: string; reason: string }
interface Requirement { title: string; kind: 'functional'|'nonfunctional'|'constraint'|'non-goal'; source: 'user'|'assumed'; ref?: string; retired?: Retirement; ext?: Record<string, unknown> }
interface Block {
  title: string; phase: PhaseId;
  status: BlockStatus; statusSince: string; statusBy: Actor; statusReason?: string;  // obrigatório em blocked e needs_rework
  owner?: string;                 // agent_id enquanto in_progress
  dependsOn: string[]; requirements: string[];
  provider?: { capability: string; provider: string; access: 'cli'|'mcp'|'api'; credentials?: string[] };  // nomes de env vars, nunca valores
  artifacts: string[];            // paths relativos ao repo
  tests: { ref: string; layer: 'unit'|'integration'|'e2e'|'visual'|'perf'|'security'|'acceptance'|'manual'; result: 'pass'|'fail'|'unknown'; at?: string; commit?: string }[];
  verification?: { passes: boolean; at: string; by: Actor; commit?: string };   // estilo ralph
  risk?: 'low'|'medium'|'high';
  retired?: Retirement;           // removido pelo Evolve; nunca apagado
  ext?: Record<string, unknown>;
}
interface BaselineEntry { n: number; at: string; decision: string; reason: string; added: string[]; retired: string[]; changed: string[]; reqAdded: string[]; reqRetired: string[] }
interface Release { id: string; version: string; at: string; baseline: number; commit: string; blocks: string[] }
```

Blocos existem em todas as fases (ex.: `B-001 Entrevista` em discover, `B-002 Plano` em route), para o diagrama mostrar o método inteiro. Fase vazia é permitida (proporcionalidade, ADR-008); gates continuam valendo. Campos futuros reservados como opcionais: `estimate`, `parent` + `epics`, `impact`. Leitores ignoram campos desconhecidos; `schemaVersion` só sobe em quebra, com `driver migrate`.

### 3. Máquina de estados

| De → Para | Quem | Exige |
|---|---|---|
| not_started → in_progress | model (tool) | todos `dependsOn` em done (user pode `--force`); grava `owner` (funciona como claim sob lock) |
| in_progress → in_review | model | `artifacts` não vazio e seção Handoff no md |
| in_progress → blocked | model, hook | `statusReason` |
| blocked → in_progress | model, user | nota no evento |
| in_review → done | model (revisor), user | `verification.passes === true`; nenhum teste `fail` |
| in_review → needs_rework | model, user | `statusReason` |
| done → needs_rework | model (Validate), user | `statusReason` |
| needs_rework → in_progress | model | |
| qualquer → not_started | só user (`driver rebaseline`) | id de decisão `D-xxx` |

Transição automática única na v1: hook `SubagentStop` move para `blocked` ("agente encerrou sem handoff") o bloco ainda `in_progress` cujo `owner` é o agente que parou. Toda transição carimba `statusSince/statusBy/statusReason` e anexa uma linha em `events.jsonl`: `{seq, ts, actor, type, block, from, to, reason?, revision}`. Histórico completo só no ledger e no git.

### 4. Gates

- Aprovação **só pelo usuário**: `/driver approve <route|release>` (comando sem turno de modelo; em headless, `driver approve` no terminal do usuário). Grava `atBaseline`.
- Revogação automática pelo escritor: `release` revoga em re-baseline, quando qualquer bloco sai de `done`, ou quando a fase recua de evolve/release; `route` revoga quando a fase recua a discover ou quando requisito é adicionado/retirado.
- `currentPhase` só avança por `driver phase advance`, que recusa cruzar gate não aprovado. Recuar é sempre permitido, com motivo.
- Hook `PreToolUse` em `Agent|Task|Workflow`: skills de fase prefixam prompts de agentes com `DRIVER-BLOCK: B-012`; o hook deduz a fase do bloco (fallback: `currentPhase`) e nega se o gate correspondente não está aprovado. Uma expressão `jq`; plan.json ausente → allow (projeto não usa DRIVER); ilegível → deny (fail closed).
- Hook `PreToolUse` em `Edit|Write|Bash`: nega escrita direta em `plan.json` e nega `driver approve` vindo do modelo via Bash.

### 5. Escrita e concorrência

- Um núcleo TS (`driver-core`: reducer puro + adaptador node) usado pela CLI `bin/driver` e, depois, pelas tools do mod (`set_block_state`, `plan_ops`). Mesma implementação de lock em todo caminho.
- Protocolo: (1) raiz = worktree principal via `git rev-parse --git-common-dir`, nunca o worktree do agente; (2) lock por `mkdir .lock` com pid+ts, stale após 30 s com pid morto, retry 50 ms até 5 s; (3) ler, checar `expectedRevision` opcional, aplicar mutação e transição; (4) `validatePlan`, rejeitar se erro; (5) `revision++`, serialização determinística (chaves ordenadas, 2 espaços), `.tmp` + fsync + rename; (6) anexar evento, soltar lock.
- Orquestrador é o escritor normal; subagents devolvem resultado estruturado. Quando um subagent precisar escrever, usa a CLI, que resolve a raiz via git. Branches de worktree nunca tocam `plan.json` (hook bloqueia), então merge não conflita.
- Mod (futuro): `$.clock.every(1000)`, redesenha só se `revision` mudou.

### 6. IDs e rastreabilidade

`R-001`, `B-001`, `D-001`, `REL-1`; alocados só pelo escritor, sob lock, a partir de `nextId`; nunca reutilizados; itens retirados ficam no arquivo com `retired`. Cadeia: `R` → `block.requirements` → `block.artifacts` + `block.tests` → `verification` → `releases[].blocks`. Retirar requisito ou bloco cita um `D-xxx`. `driver validate` detecta ids duplicados após merge humano; `driver renumber` repara.

### 7. Validação (`validatePlan`, erros e avisos)

Forma zod e formatos de id; sem duplicados; `nextId` maior que o máximo existente. Referências de `dependsOn`/`requirements` existem; sem ciclos (Kahn); sem depender de bloco de fase posterior. `statusReason` presente em blocked/needs_rework; `owner` só em in_progress. Fase além de discover ⇒ `gates.route.approved`; fase release ⇒ `gates.release.approved` e todos os blocos ativos de implement a evolve em done, requisitos ativos cobertos por bloco done com `verification.passes`. Cobertura de requisitos: aviso no Discover, erro a partir do Gate 1. `blocks/<id>.md` existe; `credentials` casam `^[A-Z][A-Z0-9_]*$`. Roda dentro de toda escrita, em `driver validate` (exit codes) e em `driver validate --replay` (dobra `events.jsonl` e compara com os status).

## Verificação

```bash
npm test && npx tsc --noEmit
node plugins/driver/dist/cli.js validate examples/web-waitlist
node plugins/driver/dist/cli.js validate examples/video-explainer
node plugins/driver/dist/cli.js export mermaid examples/web-waitlist   # confere exports/plan.mmd
bash plugins/driver/hooks/gate-check.sh < test/fixtures/hook-input-release-unapproved.json   # espera deny
```

Testes obrigatórios: dois processos gravando ao mesmo tempo não corrompem o arquivo nem duplicam ids; transição inválida é rejeitada e não altera o arquivo; re-baseline revoga `gates.release`; `validate --replay` bate com os status.

## Riscos e pendências para a próxima fase (mod)

- Capacidades de `$.fs` (create exclusivo, rename, stat) não confirmadas; conferir em `claude-code.d.ts` antes do mod. Fallback: mod chama a CLI via `$.process.spawn`.
- Não confirmado se subagent em worktree isolado pode chamar tool registrada pelo mod; fallback é a CLI.
- `DRIVER-BLOCK:` é convenção; agente sem marcador cai em `currentPhase` (seguro, mas não detecta rótulo errado).
- Merge humano de branches pode duplicar ids; `renumber` repara, não previne.
