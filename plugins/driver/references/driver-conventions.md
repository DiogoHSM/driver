# DRIVER conventions (shared by the phase skills)

Read this whole file before you touch the plan. It holds the tools, the reducer rules, the file formats and the hard rules. The six phase skills (`discover`, `route`, `implement`, `validate`, `evolve`, `release`) assume you know it. Implement, Validate and Evolve also follow `triage.md` (next to this file) for anything that would change the approved plan.

DRIVER is a method with six phases: Discover, Route, Implement, Validate, Evolve, Release. The plan is a graph of blocks stored in `.claude/driver/`. Two human gates guard it. The `route` gate sits between Discover and Route: the user approves it after Discover, and Route then advances to Implement without a gate. The `release` gate sits between Evolve and Release. Only the user can approve a gate.

## 1. Where things live

Project root `.claude/driver/` (the "driver dir"). **Artifact paths are relative to the project root.** Discover artifacts are `.claude/driver/discover/interview.md`, `.claude/driver/discover/assumptions.md`, `.claude/driver/discover/non-goals.md` and `.claude/driver/discover/summary.md`; the Route artifact is `.claude/driver/route/risks.md`. Use this form in `artifacts`, `ref` and `addArtifacts`. The table below shows paths inside the driver dir.

| Path | Who writes it |
|---|---|
| `plan.json`, `events.jsonl`, `log/`, `.mod/` | Never you. Only the tools and the CLI. |
| `blocks/B-nnn.md` | The tool creates it with `id`/`title` frontmatter, a `# B-nnn title` heading and four empty sections. You fill it only with `mcp__driver__block_doc`, never with Write, Edit, `sed`, redirection or heredocs. |
| `requirements/R-nnn.md` | `req.add` may create a stub. You fill it only with `mcp__driver__req_doc`, never with Write, Edit, `sed`, redirection or heredocs. |
| `decisions/D-nnn.md` | The tool creates it on `decision.add` (`id`/`title` frontmatter, the reason below). You normally do not edit it. |
| `discover/interview.jsonl` | Never you. Only the CLI, through `mcp__driver__discover_log`. |
| `discover/interview.md`, `assumptions.md`, `non-goals.md` | Never you. Generated by the CLI from `interview.jsonl`. Read only. |
| `discover/summary.md` | You, with Write (Discover step 7). Read it first if it exists. |
| `route/risks.md`, `route/summary.md` | You, with Write. Read first if the file exists. |
| `validate/B-nnn.md`, `evolve/review.md`, `evolve/learnings.md`, `release/checklist.md` | You, with Write (Validate, Evolve and Release). Read first if the file exists. |
| `backlog.jsonl`, `backlog.md` | Never you. Only the tool: `mcp__driver__backlog` writes `backlog.jsonl` and regenerates `backlog.md`. |
| `exports/plan.mmd` | `driver export mermaid`. Gitignored, never an artifact. |

## 2. Tools

Write to the plan only through the first three tools below. Pass `expectedRevision` (the `revision` from your last status call) to every write. The other tools, `mcp__driver__discover_log` (the Discover interview), `mcp__driver__block_doc` (block documents), `mcp__driver__req_doc` (requirement documents) and `mcp__driver__backlog` (items for the next cycle), never touch the plan.

### `mcp__driver__plan_status`

Read-only. Input: `scope` (`summary` | `phase` | `block`), `phase`, `block`. Scope `summary` returns the phase, gates, counts, ready blocks, blocks in progress and blocked blocks, with bare ids and no titles, plus `rework` (blocks in `needs_rework`), `resumable` (see the reducer rules), `openBehind` (earlier phases with unfinished work), `afterBaseline` (blocks added after the baseline) and `reqsAfterBaseline` (the same for requirements). To find a block by title, call it with `scope: "phase"` and `phase: "<phase>"`: that returns each non-retired block of the phase with `id`, `title`, `status` and `deps`. Match by title. Scope `block` (with `block: "B-nnn"`) returns one block record and an excerpt of its doc. Call it first, and again after each batch.

### `mcp__driver__plan_ops`

Input: `{ "ops": [...], "expectedRevision": 12 }`. One to 25 ops, applied atomically (all or nothing, one revision). Op shapes:

```json
{"op":"block.add","title":"Landing page UI","phase":"implement","dependsOn":["B-002"],"requirements":["R-001"],"risk":"medium",
 "provider":{"capability":"database","provider":"supabase","access":"cli","credentials":["SUPABASE_URL"]}}
{"op":"block.set","id":"B-003","patch":{"addArtifacts":[".claude/driver/discover/interview.md"],"risk":"high"}}
{"op":"req.add","title":"Visitors can join with an email","kind":"functional","source":"user"}
{"op":"req.add","title":"Works on mobile","kind":"nonfunctional","source":"assumed","ref":".claude/driver/discover/assumptions.md"}
{"op":"decision.add","title":"Project size class: S","reason":"User estimated a few days"}
{"op":"block.retire","id":"B-004","decision":"D-003","reason":"Superseded by B-009"}
{"op":"req.retire","id":"R-005","decision":"D-003","reason":"Dropped by the user"}
{"op":"phase.advance"}
```

Rules:

- `block.add`: `title` and `phase` are required. `dependsOn`, `requirements`, `risk` (`low` | `medium` | `high`) and `provider` are optional. `provider.access` is `cli`, `mcp` or `api`. `credentials` holds env var names only (`^[A-Z][A-Z0-9_]*$`).
- `req.add`: `kind` is `functional`, `nonfunctional`, `constraint` or `non-goal`. `source` is `user` or `assumed`. `ref` is optional.
- `block.set` patch keys: `title`, `dependsOn`, `requirements`, `provider`, `artifacts` (replace), `addArtifacts` (append), `tests`, `addTests`, `risk`, `verification`. Anything else is refused.
- `verification` needs `passes`, `at` and `by` to pass validation. The system overwrites `at` and `by` with the real time and actor, so send placeholders: `{"passes":true,"at":"2026-01-01T00:00:00Z","by":{"kind":"model","id":"main"}}`. The CLI does the same in one flag: `driver block set B-001 --verified true`.
- **The `"$n"` rule.** Inside one batch, `"$0"` is the id created by the first op that creates something, `"$1"` the second, and so on. Only creating ops count (`block.add`, `req.add`, `decision.add`), in batch order. Example: ops `[req.add, req.add, block.add]` create `$0` and `$1` (requirements) and `$2` (the block). Use `"$n"` in `dependsOn`, `requirements`, `decision` and `id` fields. Across batches use the real ids from the result (`created B-004, B-005`).
- The tool refuses `gate approve`, `rebaseline`, forced moves and anything not listed above.

### `mcp__driver__set_block_state`

Input: `block`, `status` (`in_progress` | `blocked` | `in_review` | `done` | `needs_rework`), `reason`, `owner`, `expectedRevision`. It cannot move a block back to `not_started`.

### `mcp__driver__discover_log`

Silent log of the Discover interview. Input: `{ meta?, nodes?, nonGoals? }`, all optional.

- `meta`: `goal`, `class` (XS | S | M | L), `domain`, `language`, `stage` (core | areas | summary | closed), `areas`, `chosenAreas`, `checkpoint` (none | pre-mortem | red-team | socratic | skipped), `accepted` (boolean, the user's explicit acceptance of the summary), `batchApplied` (string).
- `nodes[]`: `id` (Q-nn; omit to create, which needs `question` and `kind`), `question`, `area` ("core" or the area name), `dependsOn`, `kind` (fact | decision), `status` (open | researching | settled | assumed | deferred), `answer`, `source` (user | research | assumed), `options`, `why` (required when `status` is assumed), `requirement` (R-nnn).
- `nonGoals[]`: `id` (N-nn; omit to create), `statement`, `reason`, `requirement`.

Updates are by id; an absent field keeps its value. A node that becomes `assumed` gets an `A-nn` automatically. The result lists created ids, counts per status and the frontier (open nodes whose `dependsOn` are settled or assumed). A call with no keys returns whether an interview exists (`exists`), the current state and the frontier: use it to resume. A new node cannot depend on a node created in the same call: create the parent first. CLI equivalent: `driver discover log` (JSON on stdin) and `driver discover show`.

The tool appends to `.claude/driver/discover/interview.jsonl` and regenerates `interview.md`, `assumptions.md` and `non-goals.md`. Never edit those four files. Never use `sed`, shell redirection or heredocs on anything under `.claude/driver/`: use the tools, and Write only for `discover/summary.md`, `route/risks.md`, `route/summary.md`, `validate/B-nnn.md`, `evolve/review.md`, `evolve/learnings.md` and `release/checklist.md` (Read first if the file exists).

### `mcp__driver__block_doc`

Silent writer of block documents. Input: `{ blocks: [ { id: "B-004", spec?: string, acceptance?: string[], notes?: string, handoff?: string } ] }`, 1 to 30 entries per call. It rewrites only the named sections of `blocks/B-nnn.md` (`## Spec`, `## Acceptance criteria` as a checklist, `## Notes`, `## Handoff`) and keeps the frontmatter, the heading and the sections not named; an absent key leaves that section as it is. It refuses an unknown id and a block that is `done` or retired; otherwise any section may be written. A refusal changes nothing. Output: one line per block. `notes` keeps the `Input:`, `Output:`, `Risk:`, `Provider:` lines. Never edit `blocks/B-nnn.md` with Write, Edit, `sed`, redirection or heredocs: use this tool.

### `mcp__driver__req_doc`

Silent writer of requirement documents. Input: `{ requirements: [ { id: "R-003", statement?: string, acceptance?: string, origin?: string, notes?: string } ] }`, 1 to 30 entries per call. It rewrites only the named sections of `requirements/R-nnn.md` (`## Statement`, `## Acceptance signal`, `## Origin`, `## Notes`), keeps the frontmatter, creates the file if it is missing, and refuses unknown or retired requirement ids. All or nothing. Never edit `requirements/R-nnn.md` with Write, Edit, `sed`, redirection or heredocs: use this tool.

### `mcp__driver__backlog`

Silent store of items for the next cycle. Input: `{ items?: [ { title, detail?, origin?, decision? } ] }`, 1 to 20 entries. With items it appends them to `backlog.jsonl` and regenerates `backlog.md`; `origin` says what surfaced the item (`validate/B-015.md`) and `decision` the D-nnn that deferred it. With no items it returns the current backlog. It never changes the plan or its revision. Never edit `backlog.jsonl` or `backlog.md` by hand.

### CLI fallback

If the tools are not available, use Bash: `driver <command>`, or `node ${CLAUDE_PLUGIN_ROOT}/dist/cli.js <command>`. Useful commands: `init <name>`, `status`, `validate`, `export mermaid`, `block set <id> --verified true`, `block status <id> <status> [--reason ...]`, `req add`, `phase advance`, `decision add`, `backlog show`, `release add --version V --commit SHA [--blocks B-001,B-002]` (Release only; without `--blocks` it records every `done` block). Batches go through `driver apply` with the same JSON on stdin. Use a quoted heredoc, which keeps `"$n"` literal and passes the guard:

```
driver apply <<'EOF'
{"ops":[...],"expectedRevision":12}
EOF
```

Never use an unquoted heredoc delimiter, and keep backticks out of the command line.

### Revisions and refusals

Keep the `revision` from your last status call and pass it as `expectedRevision`. A stale revision is refused: call status again, check what changed, then redo the write. A refusal always carries a reason. Read it, fix the cause, then call again. Never retry the same call blindly, and never work around a refusal with a different path.

## 3. Reducer preconditions

Legal block moves (from `src/state-machine.ts`). Any move not listed is refused:

| From | Legal moves |
|---|---|
| `not_started` | `in_progress` |
| `in_progress` | `in_review`, `blocked` |
| `blocked` | `in_progress` |
| `in_review` | `done`, `needs_rework` |
| `done` | `needs_rework` |
| `needs_rework` | `in_progress` |
| any | `not_started` (only the user, through rebaseline) |

The only legal exit from `done` is `needs_rework`. Discover step 10 (rework before the gate is approved) uses it, and so do triage, Validate and Evolve when a finding makes a `done` block wrong. Nothing else moves a `done` block.

| Move | Requires |
|---|---|
| block to `in_progress` (from `not_started`) | every `dependsOn` block is `done`, and the block phase is at or before the current phase |
| block to `in_review` | at least one artifact on the block, and a filled `## Handoff` section in its `blocks/B-nnn.md` |
| block to `done` | `verification.passes === true` and no test record on the block with `result: "fail"` |
| block to `blocked` or `needs_rework` | a `reason` |
| `phase.advance` to route | gate `route` approved by the user |
| `phase.advance` to release | gate `release` approved by the user |
| `block.retire`, `req.retire` | an existing decision id and a reason |
| `needs_rework` | clears the old verification, so redo review and verification |

The dependency check applies only to the move from `not_started` to `in_progress`. Resuming from `blocked` or `needs_rework`, and closing from `in_progress`, do not check dependencies, so the skills check them.

`phase.advance` only moves to the next phase. It does not refuse because work is still open behind (only the two gates above refuse; `driver validate` merely warns with `phases.openBehind`, and errors at release). So Implement, Validate and Evolve check `currentPhase` and `openBehind` themselves before they advance.

Coverage: a requirement that is not a non-goal and has no block gives a `req.coverage` warning. It is only a warning until Release.

## 4. File formats

Templates and descriptions are in the skills (`discover/templates/`, `route/templates/`, `validate/templates/`, `evolve/templates/`, `release/templates/`). The shared triage rules for Implement, Validate and Evolve are in `references/triage.md`. Summary:

- `discover/interview.md`, `assumptions.md`, `non-goals.md`: generated read-only views of `interview.jsonl` (see the `discover_log` tool). Descriptions in `discover/templates/`.
- `discover/summary.md`: the text the user accepts (goal, what will be built, what the user decided, what the model decided with reasons, what stays out, open questions, class). Structure in `discover/templates/summary.md`.
- `requirements/R-nnn.md`: frontmatter `id`, `title`, `kind`, `source`; sections `## Statement`, `## Acceptance signal`, `## Origin`, `## Notes`.
- `blocks/B-nnn.md`: `## Spec`, `## Acceptance criteria`, `## Notes` (`Input:`, `Output:`, `Risk:`, `Provider:`), `## Handoff`. Keep the section order. Never rename a heading.
- `route/risks.md`: risk matrix plus a definition of done per phase.
- `route/summary.md`: the plan the user confirms (blocks by phase, count against the range, critical path, high-risk blocks). Structure in `route/templates/summary.md`.
- `validate/B-nnn.md`: the validation report of one validate block. Structure in `validate/templates/report.md`.
- `evolve/review.md` and `evolve/learnings.md`: the cycle review and the learnings. Structure in `evolve/templates/`.
- `release/checklist.md`: the release checklist. Structure in `release/templates/checklist.md`.

Handoff: when you finish a block, write two to five lines under `## Handoff` through `mcp__driver__block_doc` (what was delivered, where, what the next block needs to know). The reducer refuses `in_review` while it is empty.

## 5. Hard rules

1. Never approve a gate and never imply it is approved. Only the user can, by typing `/driver approve route` (or `/driver approve release`) in the composer or pressing Approve in the pane (the button reads "Approve route gate" or "Approve release gate"). A new baseline is confirmed the same way, by the button "Confirm baseline N" or the command `/driver baseline`. Say what to type or press, then end your turn.
2. Never rebaseline and never pass `--force`. If a baseline change is needed, tell the user.
3. Never write `plan.json`, `events.jsonl`, `log/` or `.mod/`, by any route (Write, Edit, Bash redirection, scripts). Read `plan.json` with Read only.
4. Never delete a block, requirement or file in the driver dir. To remove something from the plan, retire it with `block.retire` or `req.retire` citing a decision made by `decision.add`.
5. Credentials appear only as env var names (`SUPABASE_URL`). Never write a value, never ask the user to paste one.
6. Subagents never write to the plan. They get read-only research tasks and are told in their prompt not to call any `mcp__driver__*` tool; the mod also refuses plan writes from subagents. Only you call the plan tools. A subagent may write a file only when you gave it that exact path. The one exception: a subagent spawned by Implement with the marker `DRIVER-BLOCK: B-nnn` may call `mcp__driver__block_doc` for the Handoff of its own block, and no other `mcp__driver__*` tool.
7. A work product is not proof. A block is `done` only when the evidence says so (a passing check, or the user's explicit acceptance).
8. If a hook or the tool denies an action, stop and tell the user what was denied. Do not look for another way.

## 6. Language

Talk to the user in the language they write in. Questions, option labels (including "(Recommended)", "Not sure" and "That is enough, summarize", translated) and summaries use that language. `discover/summary.md` and `route/summary.md` are user documents, written entirely in the user's language, headings included. In every other file, headings, ids, keys and table headers stay in English so that tools and later skills can read them. Statements inside the files (requirement text, answers) follow the user's language.
